# Coding standards

Read during review. Terms as defined in `GLOSSARY.md`.

## Judgement calls

1. **The Field is the truth.** When the Field and the mirror disagree, code reconciles toward the Field (`Session.syncFromField`). Code that makes the mirror win is wrong unless the engine just produced that state and `render()` is about to land it in the Field.
2. **Every write to the Field goes through `Session.render()`.** It keeps `lastRendered` correct, which is how a later sync tells a user's mouse click from our own cursor. A `field.setValue` or `field.setSelection` call anywhere else is a bug. The render path includes `Session.finishRender`, which `render()` and a settled asynchronous write (`writeSettled`) both call: the cursor set there is part of the render.
3. **Engine semantics are upstream.** When behaviour differs from Vim's `:help`, the fix is an upstream issue or an entry under "Accepted limitations" in `DESIGN.md`, never a patch in the bridge. The bridge adapts the engine to the page (focus, input field, undo grouping); it does not change what a key means.
4. **Insert mode stays native.** The whitelist in `isInsertModeVimKey` (`src/bridge/Session.ts`) is the only place a key is taken from Insert mode, and adding one needs a decision recorded in `DESIGN.md`. The one extension is the keys that complete a whitelisted key the engine is still waiting on (the register after `Ctrl-r`). The one exception (#52, ADR 0008): while a VimText write to a contenteditable Field is still settling, Insert typing (a character, Backspace, a multi-line host's Enter) goes into the mirror (`Session.typeWhileWriting`) and lands with the merged write, because the caret is not yet where the text goes; any other key stays the page's. So does typing while the caret VimText set is still settling (#64, `Field.selectionSettling`): the page's editor may not have taken it yet.
5. **A routing or lifecycle change names its coverage.** A change to key routing, the render path, or Session lifecycle states which Modes (Normal, Visual, Insert, Replace) and Field placements (textarea, Single-line, a Field inside an open shadow root) it covers, with a test for each it touches, and re-reads the `GLOSSARY.md` terms it touches (Activate, Start Mode, Session State), correcting any that no longer describe the behavior: the M2 part 1 review let a Session lifecycle change through while the glossary still defined Activate without the Normal Start Mode and kept an Attach/Detach term for behavior never built. Replace mode and shadow-root Fields are the usual omissions: the M2 review found an Enter swallow that broke Replace mode and a disposal observer that never saw a shadow tree.
6. **Tests observe from outside.** A test feeds keys and asserts on what the user and the page see: the Field's value and selection, the Status Line text, the page's log. Reaching into the mirror, the engine's state, or the Status Line host's shadow DOM is a smell; drive the command line through the Session's own `status` instead. The one sanctioned read of the host is the `statusText` helper in `tests/e2e/extension.ts` and its unit-test twin: e2e has no Session handle, and the helper returns exactly the text the user sees. A behaviour that depends on the order of listeners (the document capture listener, the Status Line's command-line input, the engine's dialog) is proven by an e2e test: a unit test's `dispatchEvent` runs microtasks only after the whole dispatch, so it cannot see a listener that fires after ours. The M3 part 1 review found ex history snapshotted one key late behind a green unit test (`docs/engine-seams.md`, "Command-line keys").
7. **A test claims only what it asserts.** Its name and comments describe the assertion, not a hoped-for property. "No churn" with a value-equality check is a false claim when the value is static only because the page's filter is idempotent. An e2e that accepts more than one outcome (a burst whose key may land as the person's own or as a write) names, in a comment, the test that pins each outcome deterministically, and the reviewer checks that a run takes the path the test exists for: the Slack burst accepted either outcome and took the refused path it was written for in none of 10 runs (#73).
8. **A documented fallback is tested with the thing absent.** When `DESIGN.md` or an ADR says VimText falls back where a browser lacks an API (Firefox and `location.ancestorOrigins`), the code reads that API as optional and a unit test passes an object without it. TypeScript's DOM lib declares Chrome-only properties as required, so the typechecker never sees the throw; the M2 part 2 review found `siteOrigin` reading `ancestorOrigins.length` under docs that promised a Firefox fallback.
9. **Engine-global state is tested with two Fields Activated at once.** Mappings, a Plugin's armed catch-all binding, registers and Session State are one object per page, shared by every Session in the frame. A test with one Field cannot see a binding that leaks into the next Field or one that the next Activation's `mapclear` happens to wipe: the M3 part 2 review found a surround wait armed in one Field swallowing the first key typed in another, behind single-Field tests that were green because Activation had cleared it by accident. A change to state the engine keeps per page comes with a test that Activates two Fields up front and drives the second.
10. **A feature diff edits settled docs by addition or factual correction only.** A new limitation, a new seam, a sharper example: fine. A changed sentence in `DESIGN.md`, `GLOSSARY.md`, an ADR or this file is a finding unless the commit names it as the correction of an engine fact that turned out wrong, or carries the owner's decision (`Owner-decision: #<issue>`, which the commit-msg hook requires for this file and existing ADRs). The M4 part 2 run widened rule 4 twice; the second widening (#64) had no owner decision behind it. The M3 part 2 review found three: a binding API named wrongly in the docs (a correction, kept), a limitation flipped to describe behaviour Vim does not have (reverted), and a glossary term widened past the grilling's wording (an owner's call, flagged).
11. **A fix's regression test is red without the fix.** The reviewer runs it against `main`'s source (the recipe under "Verify a red on `main` claim" in `docs/agents/issue-tracker.md`) and sees it fail on the reported symptom; a test that passes either way locks nothing down. The #38 fix first carried a second test, for a Field widened between focuses, that was green with the fix reverted. A workaround whose cause was not found is a fix like any other: recording it in `DESIGN.md` does not excuse the red test (#52 shipped a synthetic `selectionchange` "cause not pinned down", and the #61 e2e passes either way).
12. **A browser fact in the docs names the test that pins it.** A sentence in an ADR, `DESIGN.md`, a spec or `docs/engine-seams.md` that says how Chromium behaves (an event it fires, a command's markup, how a selection reads) is backed by a test in `tests/unit/chromium-facts.test.ts`, under a `describe` named after the engine-seams entry, observed on a bare page with no VimText code; a fact with no test is a finding, and so is a probe test deleted once the code works. The M4 spec, ADR 0007 and two tickets said editing commands fire `beforeinput`; the implementers' probes showed they do not and were deleted, and the pinned file then corrected two engine-seams entries on its first run. Engine facts about `@replit/codemirror-vim` are pinned by their grep targets in the engine source instead. A fact about the content script's isolated world (what a page listener sees of an event the content script dispatches) is pinned by an e2e test against the built extension, which the entry names: a unit test runs in one JavaScript world and cannot show it ("beforeinput from the isolated world").
13. **An edit VimText made is replayed from its changes, never from a diff of the texts.** When code needs to know what the mirror's own edit did (to keep, drop or move part of it), it reads the mirror's ChangeSet. A text diff guesses wherever the same characters stand side by side: a typed line break beside an empty line put the kept typing on the empty line and lost it, past two reviews (#73). `diffText` is for a change only the page made, where the two texts are all VimText has.

## Mechanical

Enforced in `npm run check`, listed here so the reviewer knows it is covered:

- `tools/check-imports.mjs`: `@replit/codemirror-vim` and `@codemirror/{view,commands,language,search}` are imported only under `src/engine/`. `@codemirror/state` is shared vocabulary (positions, selections) and may be used anywhere in `src/`.
- `tools/check-imports.mjs`: `chrome.*` appears under `src/` only in the adapter files its `chromeAdapters` set names (the tool is the one list). Everything else, `src/content/` included, runs in a plain Chromium page so the unit suite can drive it.
- Playwright `failOnFlakyTests` (`playwright.config.ts`): an e2e test that passes only on its retry fails the gate; the retry stays so its trace tells a flake from a regression.
- `.husky/commit-msg` (`tools/check-owner-decision.mjs`): a commit that changes this file or an existing ADR carries an `Owner-decision: #<issue>` trailer (rule 10).
- `.husky/pre-push`: when the push touches `src/field`, `src/bridge` or `tests/fixtures`, `npm run test:e2e:editors` runs the four rich-editor specs again, five times each on four workers. The gate's single worker hid #64, a keystroke lost to Slate's late rendering.
- `knip` (`knip.json`): no unused files, exports, exported types, or dependencies. It does not see unused interface or class members; those stay a reviewer's call.
- `tests/node/*.test.ts`, the Node project of `npm test` (`vitest.config.ts`): repo-wide consistency checks that read files and spawn processes, which the Chromium project cannot. Today: `manifest.json` and `package.json` agree on the version, the failure naming both (`versions.test.ts`); every manifest permission and host match pattern is named in `PRIVACY.md` and under the listing's "Permission justifications" heading in `docs/store/listing.md`, the tokens derived from the manifest so a new permission is looked for by its own name (`permissions.test.ts`); the manifest `description` is the summary sentence in that listing and fits the store's 132 characters (`summary.test.ts`); `tools/package.mjs`, run as a child process against a throwaway repository, refuses a version mismatch, a dirty tree and a wrong `--expect-tag`, and zips `dist/` with the manifest at the zip root (`package.test.ts`); the release notes in `docs/store/announcements.md` hold no `<PLACEHOLDER>` token, since they become the tag message (`release-notes.test.ts`); the store icon and promo tiles have the store's sizes and transparency (`store-art.test.ts`). Adding a check is one new `tests/node/<name>.test.ts` file; `tests/node/repo.ts` resolves paths against the repository root.
