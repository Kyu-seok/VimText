# Editor write paths: Lexical, Slate, Quill under `execCommand`

Research for M4 part 2 (ADR 0007): what each editor does with a write that comes from the browser's own editing, not from its API. In Chromium that write fires `input` with an editing `inputType` and no `beforeinput` (docs/engine-seams.md "Editing commands and events"). Read on 2026-11-11.

Every claim is cited to source. The rows marked **observed** come from a throwaway spike, not from source alone: Playwright 1.65 / Chromium 158.0.8127.18, the npm builds lexical 0.53.0 (+ @lexical/rich-text, @lexical/history), quill 2.0.3, slate 0.147.4 / slate-react 0.147.5 / slate-history 0.144.0. The spike ran VimText's write sequence (`setBaseAndExtent`, synthetic `selectionchange`, `execCommand`, synthetic `selectionchange`) on two paragraphs, `hello world` / `second line`. The harness is on the branch `prototype/editor-write-paths` (`spike-execcommand/`), not on main, so a fixture has to reproduce these rows before anything relies on them.

**Short version.** ADR 0007's two-way split is too coarse:

- **Quill** is a DOM-reader, like ProseMirror.
- **Lexical** is a _hybrid_. It reconciles edits that only change text-node data, refuses most structural edits, and mangles two shapes, a delete across blocks and `insertParagraph`.
- **Slate** neither reverts nor reconciles. It diverges, and its later re-render undoes VimText's write without any event.

## Lexical

Source: `facebook/lexical` main at `d6298bf1` (2026-11-11, `packages/lexical/package.json` 0.53.0). Base URL `https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/`.

**1. Events.** Root listeners: `compositionstart`/`compositionend`, `input`, `keydown`, `beforeinput` (when `CAN_USE_BEFORE_INPUT`), plus clipboard, drag and focus events ([LexicalEvents.ts#L2512-L2529](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/LexicalEvents.ts#L2512-L2529)). It registers one `selectionchange` listener per document ([#L206-L211](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/LexicalEvents.ts#L206-L211)). `$handleBeforeInput` calls `preventDefault` for every type except simple text insertion, which it leaves to the browser and records as `unprocessedBeforeInputData` ([#L1505-L1517](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/LexicalEvents.ts#L1505-L1517)).

**2. MutationObserver.** `initMutationObserver` observes `characterData`, `childList` and `subtree` ([LexicalMutations.ts#L349](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/LexicalMutations.ts#L349), [LexicalUpdates.ts#L103-L107](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/LexicalUpdates.ts#L103-L107)). `flushMutations` ([LexicalMutations.ts#L132-L332](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/LexicalMutations.ts#L132-L332)) does two things:

- `characterData`: `$handleTextMutation` re-reads `target.nodeValue` into the TextNode through `$updateTextNodeFromDOMContent`. It skips the record within 100 ms of a `textInput` event or while `beforeinput` text is pending (`shouldFlushTextMutations`, #L139-L145).
- `childList`: _revert_. The source says so: "We attempt to "undo" any changes that have occurred outside of Lexical … To the user, these will look like no-ops." Added DOM is removed (#L239) unless it is the DOM its own key renders to. Removed children are put back by `ElementNode.reconcileObservedMutation`, which moves the committed children back into place ([LexicalElementNode.ts#L1021](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/nodes/LexicalElementNode.ts#L1021)). The selection is then restored to the pre-mutation one.

**3. `input` with no `beforeinput`.** `onInput` → `$handleInput` ([LexicalEvents.ts#L1669-L1836](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/LexicalEvents.ts#L1669-L1836)). Lexical names the execCommand case itself in `$shouldPreventDefaultAndInsertText` ([#L253-L258](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/LexicalEvents.ts#L253-L258)):

```ts
// a recent beforeinput event for "textInput". If there has been one in the last
// 50ms then we proceed as normal. However, if there is not, then this is likely
// a dangling `input` event caused by execCommand('insertText').
```

- `data != null` (`insertText`): if `$shouldPreventDefaultAndInsertText` holds, Lexical applies the text itself as `CONTROLLED_TEXT_INSERTION_COMMAND` at **its own selection** and re-renders the browser's text from the model (`rerenderText`, #L1790). That happens when the selection spans nodes, is non-collapsed, crosses a format boundary, or sits at a token or segmented node. Otherwise it reads the DOM text (below).
- `data == null` (`deleteContentBackward`, `insertParagraph`): `$updateSelectedTextFromDOM` reads the text of the DOM selection's anchor text node into its TextNode ([LexicalUtils.ts#L944-L983](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/LexicalUtils.ts#L944-L983)). `$flushMutations` (#L1833) then runs the observer logic above synchronously, inside the `input` handler.
- Selection: an update triggered by `input` keeps the editor's _previous_ selection. `useDOMSelection` is true only for `selectionchange`, `beforeinput`, composition, selection keydowns and a few others ([LexicalSelection.ts#L3655-L3666](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/LexicalSelection.ts#L3655-L3666)). So VimText's synthetic `selectionchange` before the command (`settleEditor`, src/field/editingCommands.ts) is what makes Lexical apply a controlled insertion at the right place. Without it Lexical would insert at the Normal-mode cursor's one-character selection.
- First-party tests drive Lexical with `execCommand` in Chromium. "Chromium and Firefox dispatch no beforeinput for execCommand, so the engine edits the DOM natively and only the MutationObserver sees it" ([ManagedLineBreakObservedRemoval.test.ts#L425-L431](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/__tests__/browser/ManagedLineBreakObservedRemoval.test.ts#L425-L431)). [NativeTextInsertion.test.ts#L117-L201](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/__tests__/browser/NativeTextInsertion.test.ts#L117-L201) asserts that `insertText` at a caret, over a selection, and in another paragraph lands in the model. No first-party test covers `execCommand('delete')` across blocks or `insertParagraph`.

**4. Composition.** `compositionstart`/`compositionend` handlers, then `$updateSelectedTextFromDOM(true, …)` on end (#L2018). It is the same DOM-reading path as (3), which is why (3) exists.

**5. Multi-block.** Structure goes through the `childList` revert, while text-data changes in the same write are kept. That predicts mixed results, and the spike shows them:

- Delete across blocks: both blocks keep their remaining text, but the merge is reverted.
- Delete of whole blocks or of only the boundary: refused.
- `insertParagraph` mid-block: the split is reverted, but Chromium's split had already moved the prefix into a new text node, so the prefix is lost from DOM and model alike.
- `insertText` over a range crossing blocks: works, because it takes the controlled path (Lexical's own test, [#L489-L553](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/__tests__/browser/ManagedLineBreakObservedRemoval.test.ts#L489-L553); observed).

**Observed, not found in source:** `execCommand('insertText', false, '')` over a cross-block range deleted it _and merged the blocks_ in the model (`hello woond line`). Likewise `J` written as boundary `delete` + `insertText(' ')` merged correctly: the refused delete left the cross-block selection in place, and the controlled insertion then replaced it.

**6. Selection.** The document `selectionchange` handler calls `onSelectionChange` → `updateEditorSync` synchronously ([#L306-L360](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/LexicalEvents.ts#L306-L360), [#L2325-L2470](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/LexicalEvents.ts#L2325-L2470)). It does not check `isTrusted`; the target `document` resolves through `getDOMSelectionFromTarget`. There is one skip: when Lexical itself just set the DOM selection, `isSelectionChangeFromDOMUpdate` swallows an event at the same mid-text points.

**7. Undo.** `@lexical/history` records any update with dirty nodes, whatever its source (`createMergeActionGetter`, [lexical-history/src/index.ts#L281-L433](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical-history/src/index.ts#L281-L433)). Changes of the same type within the delay merge into one entry. A reverted mutation leaves no dirty node and no entry.

**8. Caveats.** The root gets `white-space: pre-wrap` from `setRootElement` ([LexicalEditor.ts#L1748-L1755](https://github.com/facebook/lexical/blob/d6298bf1e0f0d5fb7e91004279bd4e2075121afb/packages/lexical/src/LexicalEditor.ts#L1748-L1755)), so `insertText` writes plain spaces. This code moves fast: the mutation and slot code cites issues up to #9363. Pin the fixture to an npm version and re-run on upgrade. The repo now redirects as `meta/lexical`.

## Slate (slate-react)

Source: `ianstormtaylor/slate` main at `fd42a804` (2026-11-07): slate-react 0.147.5, slate 0.147.4, slate-dom 0.147.3, slate-history 0.144.0. Base URL `https://github.com/ianstormtaylor/slate/blob/fd42a8046db8da329f4584dcf2a68ac7abd3137b/packages/slate-react/src/`.

**1. Events.** A native `beforeinput` listener (`onDOMBeforeInput`) is attached when `HAS_BEFORE_INPUT_SUPPORT` ([editable.tsx#L1055-L1067](https://github.com/ianstormtaylor/slate/blob/fd42a8046db8da329f4584dcf2a68ac7abd3137b/packages/slate-react/src/components/editable.tsx#L1055-L1067)). It calls `preventDefault` unless the insertion is "native", meaning a single character with no marks at a safe position ([#L739-L893](https://github.com/ianstormtaylor/slate/blob/fd42a8046db8da329f4584dcf2a68ac7abd3137b/packages/slate-react/src/components/editable.tsx#L739-L893)). It then maps `inputType` to `Editor.*` calls (#L907-L1045). React handles `onInput`, `onKeyDown` and the composition events. A document `selectionchange` listener is at #L1133-L1148.

**2. MutationObserver.** None on desktop. `RestoreDOM` is a pass-through unless `IS_ANDROID` ([restore-dom.tsx#L82-L84](https://github.com/ianstormtaylor/slate/blob/fd42a8046db8da329f4584dcf2a68ac7abd3137b/packages/slate-react/src/components/restore-dom/restore-dom.tsx#L82-L84)), and the Android input manager is gated the same way ([use-android-input-manager.ts#L26-L29](https://github.com/ianstormtaylor/slate/blob/fd42a8046db8da329f4584dcf2a68ac7abd3137b/packages/slate-react/src/hooks/android-input-manager/use-android-input-manager.ts#L26-L29)). The desktop observers are temporary: `useCompositionDOM` exists only during a composition, to undo IME `childList` changes, and `useNativeFormatDOM` handles `format*` input. Neither runs for `insertText`/`delete`/`insertParagraph`.

**3. `input` with no `beforeinput`.** `onInput` ([editable.tsx#L1348-L1443](https://github.com/ianstormtaylor/slate/blob/fd42a8046db8da329f4584dcf2a68ac7abd3137b/packages/slate-react/src/components/editable.tsx#L1348-L1443)) handles only:

- the Android manager;
- `format*` (revert the DOM, reselect);
- running `deferredOperations` from an earlier native insertion;
- `handleNativeHistoryEvents` when unfocused.

Nothing reads DOM text into the model. So an `execCommand` write changes the DOM only.

The DOM goes back later. `TextString` renders a memoized `<span>` and fixes it in a layout effect that runs on every render: `if (ref.current.textContent !== text) ref.current.textContent = text` ([string.tsx#L62-L120](https://github.com/ianstormtaylor/slate/blob/fd42a8046db8da329f4584dcf2a68ac7abd3137b/packages/slate-react/src/components/string.tsx#L62-L120)). The next render of that leaf therefore silently replaces VimText's text with the model's. Observed: after `insertText('XY')`, a real keystroke elsewhere in the same block left `hello worldZ`, with `XY` gone. Elements the browser added or removed (a merge, a split) are React-owned DOM that React does not know changed. What React does at the next re-render of that block is **unconfirmed**; a `removeChild` error or a duplicated block are plausible.

Extensions are the documented outside source of edits, and they arrive as **synthetic `beforeinput`**: "Some IMEs/Chrome extensions like e.g. Grammarly set the selection immediately before triggering a `beforeinput` expecting the change to be applied to the immediately before set selection." That comment sits at `flushDOMSelectionChange()` ([#L717-L721](https://github.com/ianstormtaylor/slate/blob/fd42a8046db8da329f4584dcf2a68ac7abd3137b/packages/slate-react/src/components/editable.tsx#L717-L721)). [slate#6197](https://github.com/ianstormtaylor/slate/issues/6197) reported that 0.128.0 ignoring untrusted `beforeinput` broke Text Blaze, Grammarly, Harper and ProWritingAid, and it was reverted in #6198 with regression tests in #6199. No `isTrusted` check exists at this commit (grep).

**4. Composition.** On desktop Chrome, `compositionend` inserts `event.data` through `Editor.insertText` after `compositionDOM.restore()` undoes the IME's DOM changes ([#L1661-L1735](https://github.com/ianstormtaylor/slate/blob/fd42a8046db8da329f4584dcf2a68ac7abd3137b/packages/slate-react/src/components/editable.tsx#L1661-L1735)). It reads the event, not the DOM, so composition offers no fallback path either.

**5. Multi-block.** There is no read path, so structural changes diverge exactly as text changes do (observed: merge and split both left the model unchanged).

**6. Selection.** `onDOMSelectionChange` is throttled to 100 ms ([#L326-L425](https://github.com/ianstormtaylor/slate/blob/fd42a8046db8da329f4584dcf2a68ac7abd3137b/packages/slate-react/src/components/editable.tsx#L326-L425)) and scheduled through `debounce(…, 0)` (#L429-L431). A synthetic `selectionchange` is taken, but asynchronously; only `beforeinput` flushes it synchronously.

**7. Undo.** slate-history records `editor.apply(op)` operations ([slate-history/src/with-history.ts#L82](https://github.com/ianstormtaylor/slate/blob/fd42a8046db8da329f4584dcf2a68ac7abd3137b/packages/slate-history/src/with-history.ts#L82)). A DOM-only write produces no operation and so no entry. Observed: `editor.undo()` left the diverged DOM as it was.

**8. Caveats.** Everything here is desktop. On Android, `RestoreDOM` and the input manager change the picture: they read DOM diffs from `input` and revert `childList` mutations. `Editable` sets `white-space: pre-wrap` (#L1313).

## Quill

Source: `slab/quill` tag `v2.0.3`. Every cited file is identical on main `539cbff` except `core/quill.ts`, where only scrolling changed. Parchment is `quilljs/parchment` at `3d0b71c9` (3.0.0). Base URLs `https://github.com/slab/quill/blob/v2.0.3/packages/quill/src/` and `https://github.com/quilljs/parchment/blob/3d0b71c95c056a3fd595e7a22f7ecd221f104268/src/`.

**1. Events.** `keydown` (Keyboard module bindings call `preventDefault` for Enter, Backspace and the others). `compositionstart`/`compositionend` ([core/composition.ts#L15-L32](https://github.com/slab/quill/blob/v2.0.3/packages/quill/src/core/composition.ts#L15-L32)). `beforeinput` in two places:

- the Input module, only for `insertText`/`insertReplacementText` with a non-collapsed target range, which it applies through `updateContents` and then `preventDefault` ([modules/input.ts#L49-L76](https://github.com/slab/quill/blob/v2.0.3/packages/quill/src/modules/input.ts#L49-L76));
- the History module, for `historyUndo`/`historyRedo` ([modules/history.ts#L74-L82](https://github.com/slab/quill/blob/v2.0.3/packages/quill/src/modules/history.ts#L74-L82)).

`selectionchange` is on the document ([core/emitter.ts#L6-L17](https://github.com/slab/quill/blob/v2.0.3/packages/quill/src/core/emitter.ts#L6-L17)). There is no `input` listener.

**2. MutationObserver.** Parchment's `ScrollBlot` observes `characterData` (with `oldValue`), `childList` and `subtree`, and calls `update(mutations)` ([scroll.ts#L8-L38](https://github.com/quilljs/parchment/blob/3d0b71c95c056a3fd595e7a22f7ecd221f104268/src/blot/scroll.ts#L8-L38), `update` #L183-L212). The update reconciles in three places:

- `TextBlot.update` re-reads the text ([text.ts#L80-L92](https://github.com/quilljs/parchment/blob/3d0b71c95c056a3fd595e7a22f7ecd221f104268/src/blot/text.ts#L80-L92)).
- `ParentBlot.update` detaches blots for removed DOM and creates blots for added DOM through `makeAttachedBlot` → `scroll.create(node)`. Unknown DOM is wrapped as an inline ([parent.ts#L7-L22, #L334-L391](https://github.com/quilljs/parchment/blob/3d0b71c95c056a3fd595e7a22f7ecd221f104268/src/blot/abstract/parent.ts#L334-L391)).
- Quill's `Scroll.update` emits `SCROLL_UPDATE` ([blots/scroll.ts#L280-L305](https://github.com/slab/quill/blob/v2.0.3/packages/quill/src/blots/scroll.ts#L280-L305)). `Quill` handles it by calling `editor.update(null, mutations, selectionInfo)` with source `user` ([core/quill.ts#L238-L248](https://github.com/slab/quill/blob/v2.0.3/packages/quill/src/core/quill.ts#L238-L248)).

`editor.update` takes one of two paths. A single ASCII `characterData` record goes to a fast-path diff of that text node. Anything else goes to a full `getDelta()` diff against the old Delta, with the old and new selection as diff hints ([core/editor.ts#L273-L316](https://github.com/slab/quill/blob/v2.0.3/packages/quill/src/core/editor.ts#L273-L316)). Nothing is reverted.

**3. `input` with no `beforeinput`.** Not needed: the observer callback (a microtask) picks the write up. The Input module is the only `beforeinput` path, and with no `beforeinput` it does nothing.

**4. Composition.** `compositionstart` → `scroll.batchStart()`, so mutations are held, and `compositionend` → `batchEnd()` → `update(mutations)` (composition.ts). It is the same mutation path.

**5. Multi-block.** Structural changes reconcile, because `childList` records create or detach Block blots (observed: merge, split, and `o` all correct). The new block's blot class comes from the tag and attributes Chromium cloned: an `<h1>` split stays a header (observed). Quill 2 lists are `<ol><li data-list=…>`, and a cloned `<li>` should keep `data-list`, but that is **unconfirmed**.

**6. Selection.** `selectionchange` → `setTimeout(update, 1)`. Around each mutation batch, `SCROLL_BEFORE_UPDATE` reads the native range and restores it afterwards ([core/selection.ts#L64-L100](https://github.com/slab/quill/blob/v2.0.3/packages/quill/src/core/selection.ts#L64-L100)). A script-set selection is picked up.

**7. Undo.** History records every TEXT_CHANGE (`userOnly: false` by default), merging changes within `delay: 1000` ms ([modules/history.ts#L26-L55, #L111-L135](https://github.com/slab/quill/blob/v2.0.3/packages/quill/src/modules/history.ts#L111-L135)). Observed: `history.undo()` restored every case. Several VimText writes within a second become **one** Quill undo step.

**8. Quill v1 differences.** v1.3.7 has the same Parchment observer → `SCROLL_UPDATE` → `editor.update` path ([core/quill.js#L93-L99](https://github.com/slab/quill/blob/v1.3.7/core/quill.js#L93-L99)). It has no `modules/input.js`, so no `beforeinput` handling at all, and no `core/composition.js`; v1's `Scroll.update` returns early while batching ([blots/scroll.js#L148-L160](https://github.com/slab/quill/blob/v1.3.7/blots/scroll.js#L148-L160)). `.ql-editor` is `white-space: pre-wrap` ([assets/core.styl#L51](https://github.com/slab/quill/blob/v2.0.3/packages/quill/src/assets/core.styl#L51)).

## Specs

- Input Events (editor's draft, https://w3c.github.io/input-events/): `input` "MUST [be dispatched] immediately after the DOM has been updated due to user expressed intention". A non-normative note says extensions "may modify the contents of editable elements by dispatching synthetic beforeinput events … JavaScript developers are advised to listen for these synthetic beforeinput events", and that a script-created event's `getTargetRanges()` returns the `targetRanges` from its `InputEventInit`.
- execCommand (unofficial draft, https://w3c.github.io/editing/docs/execCommand/): "Fire an event named "beforeinput" at affected editing host…". The draft says `execCommand` fires `beforeinput`; Chromium does not (docs/engine-seams.md). Lexical's test comment says WebKit does.

## What the fixtures should test

Every case runs VimText's real write path (`replaceDomRange`, synthetic `selectionchange` included). After the write, compare the projection with the editor's model (Lexical `$getRoot().getTextContent()` per block, Slate `Node.string`, Quill `getText()`). The model check is the one that matters: Slate's divergence is invisible in the DOM.

## Spike 2: synthetic `beforeinput` first, `execCommand` as fallback (2026-11-12)

Decided on in ADR 0008. Harness and raw data: branch `prototype/editor-write-paths`, `prototype/editor-write-paths/spike-beforeinput/` (`RESULTS.md` has the full case table). Same versions as above, plus ProseMirror at VimText's pins and a bare contenteditable; run both from the page and from a real MV3 content script in the isolated world.

The step: select + synthetic `selectionchange`; dispatch `new InputEvent('beforeinput', {inputType, data, bubbles, cancelable, composed, targetRanges: [StaticRange]})` on the editing host; if not `defaultPrevented`, run the `execCommand`; synthetic `selectionchange`.

- **Models come out right.** With 20 ms between steps, all 22 cases are correct in Lexical, Slate and Quill, including every Lexical failure and Slate divergence in the table above; a following real keystroke keeps them, and the editor's undo restores them. No write was applied twice: where Lexical or Slate let a simple insert through uncancelled, the fallback `execCommand`'s `input` completes it (Lexical `unprocessedBeforeInputData`, Slate `deferredOperations`).
- **ProseMirror and bare contenteditable are unchanged**, byte for byte, in every case and timing: neither cancels the event (ProseMirror's only `beforeinput` handler is an Android-only Backspace hack).
- **Isolated world works.** A page-world listener sees an `InputEvent` (`isTrusted` false) with the right `inputType`, `data`, and `getTargetRanges()` returning a `StaticRange` over the page's own text nodes; the content script reads the page's `preventDefault` back through `defaultPrevented`.
- **Delete is `deleteContentBackward`.** Lexical and Slate cancel plain `deleteContent` and do nothing. Slate ignores `targetRanges` for `delete*` and uses its selection, which it flushes from the synthetic `selectionchange` at `beforeinput`. Without `targetRanges`, Lexical's `J` is wrong.
- **Timing is the new risk.** An editor that cancels a step re-renders its DOM later (Lexical a microtask, Slate after React renders, more than one microtask). A native step right after edits stale DOM: Slate `J` duplicated text and threw a React `removeChild` `NotFoundError`; Lexical `A\nB` lost `B`. A task between steps fixes Lexical and Slate within one write. Two separate writes back to back need about 20 ms in Slate, which ignores `selectionchange` until a timer it set after rendering clears.
- **Undo**: a synchronous write is one undo step in every editor; spaced steps cost Lexical and Slate one undo each.
- Not tested: Android, other editors, a page's own extra `beforeinput` listeners.
