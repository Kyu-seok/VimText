# Engine seams

The Vim engine is `@replit/codemirror-vim` (the CodeMirror 6 adapter) over
`@replit/codemirror-vim-core` (the editor-agnostic engine). Read both from
`node_modules`; the GitHub and npm pages come back blocked or empty to fetch tools.

- Adapter: `node_modules/@replit/codemirror-vim/dist/index.js` (~1,700 lines)
- Engine: `node_modules/@replit/codemirror-vim-core/vim.js` (~7,200 lines)
- Upstream test suite: `node_modules/@replit/codemirror-vim-core/test/vim_test.js`

The bridge (`src/engine/mirror.ts`, `src/bridge/Session.ts`) depends on the seams
below. Each entry is a gotcha the source does not state; the function names in
parentheses are the grep targets. One entry per seam, as a list rather than a
table, so two branches adding an entry each merge cleanly (prettier re-pads a
whole table for one new row). `.gitattributes` merges this file with
`merge=union`: entries two branches append at the same place both land, with
no conflict. An entry both branches edited lands twice, old and new, so whoever
merges keeps the newer one.

- **Feeding keys** (adapter `vimPlugin.handleKey(e, view)`, reached as `cm.state.vimPlugin.handleKey`): takes a KeyboardEvent-shaped object and calls `preventDefault` itself when consumed. Returns false for Esc in Normal mode even when it just cancelled a pending operator or count, so the bridge re-prevents Esc whenever input was pending.
- **Key names** (engine `vimKeyFromEvent`): `' '` → `<Space>`, `Escape` → `<Esc>`. The default keymap maps `<C-[>` and `<C-c>` to `<Esc>` in Insert mode; the bridge normalises Ctrl-[ to Escape itself and never forwards Ctrl-c (copy on Windows).
- **Status and dialogs** (adapter `cm.state.statusbar`, `vimPlugin.updateStatus()`, `openDialog`, `openNotification`): point `statusbar` at your own element and the plugin renders `--MODE--`, pending keys, notifications and the `:` `/` `?` input there. `openDialog` focuses its input and calls `cm.focus()` when it closes.
- **Mode** (adapter's `vim-mode-change` listener writes `cm.state.vim.mode`): unset until the first mode change (Normal). Visual sub-modes arrive as `"visual line"` / `"visual block"`, and nothing marks the command line: the bridge translates to the closed `Mode` union in `src/engine/mode.ts` and reports Command-line from `commandLineOpen()`. A listener registered after the plugin's sees the new value. Replace mode is Insert mode to the engine (`vim.insertMode` true, `cm.state.overwrite` set), so any rule keyed on Normal must check `insertMode`, or it fires under `R`: the M3 part 2 review found the Plugin key hook holding `d` in Replace mode.
- **Focus** (adapter `CodeMirror.focus()` → `view.focus()`): override per instance to focus the Field, or the hidden mirror steals focus after every dialog. An ex command that blurs the Field must defer the blur (`queueMicrotask`) because the dialog's close re-focuses synchronously afterwards.
- **Insert-mode recording** (engine `onChange` via `cm.on('change')`, `onKeyEventTargetKeyDown` attached to `cm.getInputField()`): every mirror transaction while `vim.insertMode` is recorded for `.` and macros (adapter change objects carry no origin, which the engine treats as typed input). Override `getInputField` to return the Field element so native Backspace/Delete are recorded. A selection-only dispatch in Insert mode marks the recording `maybeReset`, like Vim after an arrow key.
- **Insert-mode pending keys** (engine `handleKeyInsertMode`, `vim.inputState.keyBuffer`): `<C-r>` is a partial match of `<C-r><register>`: the engine returns true, leaves `<C-r>` in `keyBuffer`, and needs the next key to finish. The bridge forwards keys to the engine while `keyBuffer` is non-empty even in Insert mode, where it otherwise forwards only the whitelist.
- **Dialog lifetime** (adapter `cm.state.dialog`, `CodeMirror.signal(cm, "dialog")` on `showDialog`/`hideDialog`): set for the `:` `/` `?` input and for notifications alike; cleared when either closes (`openNotification` after its `duration`). The signal on close fires before `openDialog` re-focuses the Field, so a hide keyed on "Field not focused" would flicker; the bridge keeps the Status Line while the command line has focus, and after `:wq` only, until the notice closes.
- **Command-line keys** (adapter `openDialog`'s `keydown` listener on its own `<input>`): Enter, Up and Down in the `:` `/` `?` input are handled by the dialog input's listener, never by `handleKey`, so `Session.handleKeydown` never sees them. The input lives in the Status Line's shadow root, so a document capture listener does see the keydown, but it runs before the input's listener: a microtask queued from it runs at the checkpoint after the capture listener, before the engine has run the command. Observe the result on the `dialog` signal (`Session`'s `onDialog`), not on the keydown. The M3 part 1 review found ex history snapshotted one key late behind a green unit test, because a script `dispatchEvent` defers microtasks past the whole dispatch.
- **Undo grouping** (`@codemirror/commands` history `addChanges`): userEvent `input.type.compose` always joins the previous history event; `input.type.compose.start` opens a new one. The adapter's `dispatchChange` uses `.start` for the first change of an operation. The bridge uses this to make one Insert session one undo step, joined to the command that opened it (`cw`, `o`).
- **History grouping** (`@codemirror/commands` history `addChanges`, `newGroupDelay` (500 ms default)): even a `.start` event joins the previous one when the two changes are adjacent, arrive within `newGroupDelay`, and no selection-only transaction sat between them. Two linewise puts (`yyp.`) typed within 500 ms are one undo step. Tests that chain such commands advance a fake clock between them; a person is slower than the delay.
- **External selection** (engine `onCursorActivity` → `handleExternalSelection`): a non-Vim dispatch with a non-empty selection puts the engine in Visual mode (this is how mouse drags work). An empty one in Normal mode is not clipped to the line; the bridge clips with `clipToLine`.
- **Mapping resolution** (engine `commandDispatcher.matchCommand`): a full match wins at once over a partial user mapping; there is no `timeoutlen` wait. `nnoremap <Space>x …` can never fire while `<Space>` is bound. Recorded in DESIGN.md accepted limitations.
- **User mappings** (engine `Vim.map`/`noremap`, `Vim.mapclear(ctx?)`, `defaultKeymap`): mappings are global per frame, shared by every mirror, and outlive the Session that ran them: a vimrc line removed in Settings keeps firing until something clears it. `mapclear()` partitions the user mappings off the front of `defaultKeymap` (the defaults are the trailing `defaultKeymapLength` entries), so clearing is cheap and leaves the built-ins alone. Ex errors (`Not an editor command`, `Unknown option`, `No such mapping`) are a red notice in the dialog, not a throw; `set nosuchoption` reports `suchoption` (the `no` prefix is parsed first). `ignorecase` is not an option this engine defines.
- **Ex commands** (engine `Vim.defineEx(name, prefix, fn)`, `Vim.handleEx(cm, line)`): `write` is predefined as a no-op (the bridge redefines it); `quit`, `wq`, `xit` are not defined upstream. `:s` ends with the engine's "Found N matches" notification from `doReplace` → `stop`.
- **Layout** (adapter `findPosV`, `charCoords`, `getScrollInfo` read `view.dom` and `scrollDOM`): the mirror must be laid out (`visibility: hidden` offscreen, never `display: none`) and sized to the Field's content width and height for `gj`/`gk` and `Ctrl-d`/`Ctrl-f` to mean anything. Offscreen also means unmeasured (`@codemirror/view` `ViewState.measure`, `if (!this.inView && !this.scrollTarget && !inWindow(view.dom)) return 0`): the mirror host sits at `left: -100000px` (`src/ui/StatusLine.ts`), so line heights stay the height oracle's estimates (a wrap about every 30 characters) until a dispatch sets a scroll target. Left alone, on a wide Field with long unwrapped lines, the first `j` after Activation runs `moveVertically` over the estimated blocks and lands at the end of the text (#38; `textarea.html`'s short lines never show it, the M3 part 3 screenshot fixture did). `Mirror.applyStyle` therefore dispatches a `scrollIntoView` effect: the scroll target lets the next measure run, and the first read of layout (`readMeasured`) flushes it, even when the key arrives before the animation frame.
- **Clipboard registers** (engine `RegisterController.pushText` (`registerName === '+'`), `actions.paste`): only `+` is a clipboard register (`validRegisters`; `*` is not, so `"*` is a key rewrite in the bridge). A `"+` yank calls `navigator.clipboard.writeText` synchronously inside `handleKey`. A `"+` paste calls `navigator.clipboard.readText().then(continuePaste)` with no catch: the paste lands asynchronously (through the mirror update listener), and a denied read is an unhandled rejection `handleKey` never reports, so the bridge reads first (`Session.pasteFromClipboard`). Insert-mode `Ctrl-r +` reads the register's cached text, not the clipboard.
- **Global state** (engine `getVimGlobalState_`, `Register`, `HistoryController`, `InsertModeKey`): one object per page, shared by every mirror; initialised at module load, so a restore before any Session exists is fine. `registerController.unnamedRegister` is the same object as `registers['"']`: restore with `setText` on the existing register, never replace it. `getRegister` answers the unnamed register for a name it rejects (`isValidRegister`), so restore only names it accepts. Macro replay tells an Insert-mode special key from typed text by `instanceof InsertModeKey`, so a serialized key is rebuilt with `new Vim.InsertModeKey(keyName, e)` (`src/engine/globalState.ts`); only Backspace/Delete are ever recorded, and the mirror does not replay them (upstream). Search history walks on `keyup` of Up/Down in the prompt.
- **Command matching** (engine `commandDispatcher.matchCommand`, `commandMatch`, `commandMatches`): a full match beats a partial one at once, so `d`, `c`, `y` (complete operators) and `in` (`i<register>` with `n`) resolve before a longer binding can; a `ds<character>` binding never fires. `<character>`/`<register>` may only end a binding and match any single key, so a binding whose keys are just `<character>` matches the next key whatever it is (the Plugins' one-shot catch-all). Among full matches the first in `defaultKeymap` wins, so an exact `i(` unshifted by `mapCommand` beats the stock `i<register>` for that key only. In operator-pending context (`inputState.operator` set) actions are skipped entirely. Visual `S` is `keyToKey` to `VdO`, Normal `S` to `cc`, `s` to `cl`.
- **Plugin bindings** (engine `mapCommand` → `_mapCommand` unshifts onto `defaultKeymap`; `defineOperator`/`defineMotion`/`defineAction` set a name in a module-level registry): a binding lands in the user partition that `mapclear()` wipes, so a Plugin re-binds on every Activation; a definition persists and replaces the previous one by name, with no getter, so a Plugin cannot delegate to the stock `textObjectManipulation` and must claim keys one by one. The public `mapCommand(keys, type, name, args)` builds one `[type]`/`[type]Args` pair, so an `operatorMotion` entry (an `operator` and a `motion`, each with its args, as `<SurroundDs><character>` needs) cannot be expressed through it: the bridge's `EngineApi.bindKey` calls `_mapCommand` with the whole entry.
- **Failed motion under an operator** (engine `evalInput`, `if (!motionResult) return`, `if (!newHead) newHead = copyCursor(origHead)`): a motion that returns null or undefined ends `evalInput` before the operator runs, with the input state already cleared: the one way a Plugin motion cancels its operator (`ds(` with no pair). A stock text object that finds nothing (`textObjectManipulation`'s `return null`) ends the operator the same way: `cix` stays in Normal mode (the M3 part 2 targets build probed it; an earlier version of this entry said it entered Insert). A motion cannot keep the operator pending for a later key.
- **Keymap context under an operator** (engine `commandMatches`, `if (inputState.operator) context = "operatorPending"`): while an operator is pending the matcher's context is `operatorPending`, not `normal`, so a binding with `context: "normal"` is never considered there and a text-object binding must carry no context (as the stock `i<register>` does) to serve both operator-pending and Visual. A vimrc `onoremap` is the mapping that reaches it. An exact binding without `<character>` gets no `selectedCharacter` from the matcher; the Plugin puts the character in the binding's `motionArgs`, which `evalInput` leaves alone when the input state has none.
- **Selected character under an operator** (engine `evalInput`, `motionArgs.selectedCharacter = operatorArgs.selectedCharacter = inputState.selectedCharacter`): the character a motion took (`iw`'s `w`, `f)`'s `)`) reaches the operator as `args.selectedCharacter` too, so an operator whose own binding may end in `<character>` (Visual `S{char}`) cannot tell the two apart by the argument alone; surround reads it only in Visual mode, where no motion runs.
- **Catch-all lifetime** (engine `processAction`: `clearInputState` → `CM.signal(cm, 'vim-command-done')` → `actions[name]()`; `Vim.unmap(keys, ctx)`): the signal for the command that completes a `keys: "<character>"` binding fires before the binding's action runs, and a key the catch-all resolves to `clear` fires it too, so a handler that removes the binding on the first signal after arming disarms in both cases and the action still runs in the first. `Vim.unmap` removes the first keymap entry whose `keys` and `context` both equal its arguments, so a bare `<character>` entry bound with `context: "normal"` is removed with `unmap("<character>", "normal")`.
- **Status text** (adapter `handleKey`: `vim.status += key`; `updateStatus` renders it; the adapter's own `vim-command-done` listener empties it): `vim.status` is display-only, appended for keys fed through the adapter (a Plugin Key by name included, as `<SurroundYs>`), never for keys a macro or a mapping feeds through the core. The bridge rewrites it after feeding a Plugin Key (`Mirror.showTypedKeys`) and calls `updateStatus()` again.
- **Replay** (engine `repeatLastEdit`, `executeMacroRegister`, `recordLastEdit`): both set `macroModeState.isPlaying`. `.` restores `vim.inputState = vim.lastEditInputState` and calls the operator or action directly, so during a `.` replay `inputState === lastEditInputState`; a macro feeds keys through `vimApi.handleKey(cm, key, 'macro')` one by one (property lookup on the API object). Keys with origin `mapping` are not logged into a recording macro; everything else is logged before matching. `recordLastEdit` runs for an operator and for an `isEdit` action, so a non-edit action that finishes a two-step command leaves the operator and motion as the recorded edit.
- **Taking a change back** (`@codemirror/commands` `undo`, `undoDepth`, `HistoryState` after a pop; `Mirror.undoSince`): `undoDepth` does not grow when a change joins the previous step (History grouping), so a bridge that must remove a change counts steps from a depth it noted and, with none new, undoes the joined step whole and writes back the part it keeps. A pop resets the history's `prevTime`, so the next `input.type` change opens a step of its own. The undo restores the selection the command started from, and `x`'s covers its character: a non-Vim dispatch of it is an External selection that puts the engine in Visual, so the bridge dispatches a cursor in the same breath (`Mirror.takeBackSince`). Never undo while `vim.insertMode`: the engine records the undo's change as typed text for `.`.
- **Atoms in registers** (engine `RegisterController.pushText(registerName, operator, text, linewise, blockwise)`, reached as `Vim.getRegisterController()`; adapter `getRange`, `getSelection`): every yank, delete and change stores text it read through the adapter's `getRange` (`d`, `c`, `:yank`) or `getSelection` (`y`, Visual and blockwise ops) moments before, then calls `pushText` with the text only, no position; `pushText` also does the `"+` clipboard write. A Visual `p` writes the text it replaces with `unnamedRegister.setText` directly. So the bridge (`src/engine/atoms.ts`) wraps `getRange`/`getSelection` per mirror to note each read holding a U+FFFC with the Atoms at those offsets (an `atomTable` StateField the Session refreshes from the Field after each sync and render, mapped through changes in between), and wraps the page-global `pushText` and the unnamed register's `setText` once to substitute each Atom's visible text from the newest read the stored text starts with (`cw` trims trailing whitespace; a linewise register adds `\n`). A U+FFFC no read knows (a literal one in a textarea) is stored as is. The wrapped reads return the text unchanged: reads feed edits too (`gu` and Visual `p` write back what they read), so only the register write substitutes.

## contenteditable seams

The browser's side of a contenteditable Field (`src/field/ContentEditableField.ts`,
`src/field/projection.ts`, `src/field/editingCommands.ts`, ADR 0007), as Chromium
behaves. Each Chromium fact below is pinned in `tests/unit/chromium-facts.test.ts`,
under a `describe` named after its entry, observed on a bare page with no VimText
code running; an entry that states a new one adds its test there (CODING_STANDARDS
rule 12).

- **Editing commands and events** (`document.execCommand`, `replaceDomRange`): each command fires one `input` with an editing `inputType` (`insertText`, `deleteContentBackward`, `insertParagraph`) and no `beforeinput`; real typing fires both. Under `execCommand` alone, Lexical reads a write's text changes back on `input` but reverts its structural ones, and Slate reads nothing back (a Diverged Edit), which is why each step offers a synthetic `beforeinput` first (ADR 0008; docs/research/editor-write-paths.md; Lexical pinned by `tests/e2e/lexical.spec.ts`, Slate by `tests/e2e/slate.spec.ts`). The command acts on the selection, so the write selects the diff's DOM range first; and setting a selection inside a blurred host makes it the active element again.
- **Block merges and splits** (`execCommand('delete')` across a block boundary, `insertParagraph`): deleting from the start of one block to the start of the next merges them, and the second block's first line moves into the first block's element: `dd` on a `<p>` above `<div>third<br>fourth</div>` leaves `<p>third</p><div>fourth</div>`. Same text, other markup, so an undo restores the projection exactly but not always the markup, and Chrome's `innerText` reads `<p>`/`<div>` neighbours with different blank-line counts. `insertParagraph` at the end of a block makes an empty sibling of the same tag holding a placeholder `<br>` and leaves the caret at `(newBlock, 0)`; at the end of a heading the sibling is a `<div>` (a correction found by #61: an earlier version said the same tag for every block). Pinned by `tests/unit/chromium-facts.test.ts`, "Block merges and splits".
- **Whitespace under editing** (`execCommand('delete')`, `insertText`, `keepAdjacentSpaces`): a delete that leaves a whitespace-only text node at the edge of a block removes that node, so `cw` on `quick` in `quick <b>brown</b>` loses the space; an insertion at a block's start joins the following inline (the typed word turns bold). `insertText` writes U+00A0 wherever a plain space would collapse and never converts it back. So the write widens a deletion by an adjacent space and writes the space back as part of the replacement, and the projection reads U+00A0 as a space (`renderedText`). A widened space that stood for a collapsed run of source whitespace is the whole run, so the rewrite leaves one space in the markup where the source had several (the rendered text is the same).
- **Selection round trip** (`Selection.setBaseAndExtent`, `anchorNode`/`focusNode`): Chromium keeps a set selection as given (no canonicalization into text nodes), so a position the projection hands out reads back as the same offset; an element position between blocks (`(p, 1)` after a block's text) belongs to the line of the block that contains it (`projection.fromDom`). A collapsed `(emptyBlock, 0)` is the caret in an empty paragraph.
- **Editor catch-up** (`replaceDomRange` → `settleEditor`; prosemirror-view `DOMObserver.onSelectionChange` → `flush`, `readDOMChange`): ProseMirror reads DOM changes in its MutationObserver callback, a microtask after the whole synchronous write, and its selection from `selectionchange`, which the browser fires in a later task. Left alone it reads a write against the previous key's selection: a deletion that starts before that selection's anchor is taken for Backspace (`handleKeyDown(Backspace)` on its own selection, so `x` after a cursor move deletes the wrong character and restores the right one), and an `insertParagraph` + `insertText` pair is read as one change in which Chrome's new block cloned the previous block's inline marks. Its `selectionchange` listener also flushes pending records (`takeRecords`), so the write dispatches a synthetic `selectionchange` on the host's document after selecting and after each command: ProseMirror takes the selection, applies a paragraph break as its own Enter (`looksLikeEnter`, so `splitListItem` makes a list item), and runs an input rule inside the write, where the bridge's re-read after `setValue` sees it as a Controlled Field rewrite joined to the undo step. A unit test that feeds keys without yielding to a task still needs a microtask turn per key, or ProseMirror reads two keys' writes as one. Since #52 the write is asynchronous (ADR 0008), its steps a task apart, so ProseMirror also reads each step in its MutationObserver callback before the next, and the bridge re-reads the Field once the write has settled, a task after its last step (`Session.writeSettled`); a key pressed before then is merged into the next write. Pinned by `tests/unit/prosemirror.test.ts` and `tests/unit/async-write.test.ts`.
- **Linewise writes** (`breakAtLineEnd` in `ContentEditableField`): the diff places `o`'s or a linewise `p`'s inserted `X\n` after a `\n` at the start of the next line, inside the next block (on a paragraph above a list, the first list item), and `dd`'s deleted `X\n` from the line's start to the next line's start, which merges the next block into this one's element (the paragraph below a list joins the last item). The write slides the span left by one, `\nX` at the end of the line above: the same text, written as Enter or Backspace there would be. An editor may re-render the block that `\n` made: at the end of a heading Chromium makes a `<div>` (see "Block merges and splits"), which Quill replaces with a `<p>` of its own, the DOM caret left between the blocks, and `X` typed at that caret was lost or landed in the heading (#61). So the step after a paragraph break first puts the caret where the projection, read after the re-render, puts the new line's start (`placeCaret` in `editingCommands.ts`, `ContentEditableField.caretFrom`). Pinned by `tests/unit/contenteditable-field.test.ts`, "text after a paragraph break lands on the new line…", and `tests/e2e/quill.spec.ts`, "a linewise p below a header, or P on the line below it, keeps the pasted line".
- **Marks at a write's edges** (ProseMirror inclusive marks, Chrome typing style): text inserted at the end of a mark run takes the mark, as typing there would: `J` after an italic word makes the joining space italic, a character restored by `u` at the start of a bold run is plain. `keepAdjacentSpaces` therefore takes a neighbouring space into a deletion only at a line's or a table cell's edge (where Chrome drops it); mid-line it would be written back in the style of the span's start (`cw` on the last word of a bold run turning the plain space after it bold). ProseMirror needs `white-space: pre-wrap` (its `style/prosemirror.css`): without it Chrome's `insertText` writes U+00A0, which ProseMirror keeps in its document.
- **innerText as the oracle** (`HTMLElement.innerText`, `projection.ts` `Walker`; #45, `tests/unit/projection-innertext.test.ts`): the projection equals Chrome's `innerText` on `<div>`s, lists, `pre`, `white-space: pre-wrap`/`pre-line` text, tables and collapsed source whitespace, with three deliberate departures where `innerText` is not what renders. (1) One line per block: `innerText` gives `<p>` a blank line on each side (the spec's required line break count 2), so `<p>a</p><p>b</p>` reads `a\n\nb`; a heading gets none of its own (`<div>a</div><h1>b</h1><div>c</div>` reads `a\nb\nc`) and reads blank lines only beside a `<p>` (an earlier version of this entry said Chrome gives `<h1>` its own); the projection keeps one line per block, as DESIGN.md's _Projection_ and the tracer bullet do. (2) A break that ends its block renders no line: `innerText` reads `<div>a<br></div>` and `<pre>a\n</pre>` as `a\n` (each block measures one line high), the projection as `a`. A `\n` where breaks are preserved is held like a `<br>` for this reason. (3) A `<br>` in front of a nested block: `innerText` reads a line for it and another for the block, so `one<div><br><div>two</div></div>` reads `one\n\n\ntwo` and `<div>a<br><div>b</div></div>` `a\n\nb`, while one alone on its line renders an empty line and one ending a line of text renders none (three lines, two). The projection reads `one\n\ntwo` and `a\nb`. Chromium's `insertParagraph` at the end of a bare text line above a `<div>` makes exactly that first shape, which is Gmail's compose body under `o`; before #67 a nested block dropped the held `<br>`, the write projected as unchanged and was judged refused (`tests/unit/chromium-facts.test.ts`, "a <br> before a nested block…"; `tests/unit/projection-innertext.test.ts`). So an `innerText` comparison in a test holds only on markup without `<p>`s, headings, block-ending breaks and breaks before nested blocks, and an undo that leaves the same text in other markup (a merge into a `<div>`, a `<br>` a plaintext-only host leaves ending a `<p>`) changes `innerText`, not the projection: the e2e reads Vim's text through a `"+` yank instead.
- **Whitespace in the offset map** (`getComputedStyle(…).getPropertyValue("white-space-collapse")`, `Piece.offsets`): Chrome exposes the longhand `white-space-collapse` (`collapse`, `preserve`, `preserve-breaks`, `break-spaces`); `white-space` is the shorthand. A `text` piece maps each projected boundary to a DOM offset, because a collapsed run of source whitespace is one projected space spanning the whole run and whitespace that renders as nothing (a line's start or end, between blocks, around a `<br>`) has no character: a DOM point inside a run reads as the boundary after it. `Selection.toString()` reports a collapsed run as one space, as it renders. A table cell is the one `display: table-cell` kind: the tab before each cell after the first is a gap no node owns (like a block's `\n`), and an empty cell is a zero-length `line` piece at `(cell, 0)`.
- **plaintext-only hosts** (`contenteditable="plaintext-only"`): `isContentEditable` is true, and the host computes `white-space: pre-wrap`, so its source spaces and newlines are kept and a `\n` in its text is a line break. `insertParagraph` still splits blocks (`<div>`/`<p>`, as on a `true` host), but `delete` across a block boundary leaves a `<br>` ending the merged block (`<p>jumps…<br></p>` after `dd` above a `<div>`), which the projection reads as no line. A `u` then restores the text, not the markup.
- **Lifecycle of a host** (`Sessions` `lifecycleOptions.attributeFilter`, `stillQualifies`): a host stops qualifying when `contenteditable` changes, or when `aria-multiline="false"` appears or goes (`ResolvedField.singleLine` no longer matches the Field's `singleLine`, so the Session is disposed and the next Activation makes a Field of the new kind), which arrives only as an attribute record, so both attributes are in the filter. Every edit inside a host is a `childList` record too, so the observer re-checks `stillQualifies` on each keystroke while a Session exists; `resolveField(host)` is cheap (one `isContentEditable` walk).
- **Refused edits** (`replaceDomRange`'s return, `Session.judgeWrite`): cancelling `beforeinput` does not stop an editing command, since none fires; but since #53 each step offers its own synthetic `beforeinput` first and runs no command when the page cancels it, so a page that cancels every `beforeinput` and does nothing refuses the edit (`tests/unit/refused-edit.test.ts`, "A page that cancels beforeinput"). An edit really refused shows as a write after which the projection is what it was: an editor whose `input` handler puts its markup back (the command returns true, the text is unchanged), or a selection inside a `contenteditable="false"` island (the command returns false and changes nothing; the host stays the active element). So the bridge keys refusal on the projection, not on the return value, which also covers a textarea whose page puts its value back. Fixture: `tests/fixtures/refused-edit.html`, a locked span its `input` handler restores. Notion and Slack's texty cancel a synthetic `insertParagraph` (and `insertLineBreak`) and do nothing, while taking `insertText`; an Insert-mode Enter typed while a write or the caret is settling (`typeWhileWriting`) is written that way, so its write is refused. A refused write keeps the typing in it and since it without its line breaks (`Session.typedWithoutBreaks`, #68), in Normal too, since keys typed back to back put the Esc in before the write settles: rolling back to the agreed text took the characters typed after the Enter too, which never reached the page (`tests/unit/async-write.test.ts`, "A refused line break typed while a write is pending"; Normal only in a real browser: `tests/e2e/site-shapes.spec.ts`, the Notion burst). Only the typing is kept (#73): a refused write that holds any change made outside an Insert session since the text was last agreed (a Normal or Visual command, `o`'s new line, made before Insert begins, a paste) is refused whole, so a refused `u` of `J`, `o` or linewise `p` keeps nothing; the Insert keys the engine runs (Ctrl-w, a counted insert's repeats at Esc) count as typing (`Session.commandChanges`; `tests/unit/async-write.test.ts`, "A refused line break no one typed" and "A refused line break, then Insert keys the engine runs"). In Replace an Enter is the page's own key, never written, so a refused line break comes from Insert only.
- **Selection in an open shadow root** (`document.getSelection()`, Chromium's `ShadowRoot.getSelection()`, `selectionFor` in `src/field/domSelection.ts`): a selection made inside a shadow tree (by the user, by typing, or through the shadow root's own selection) reads through the document as a point in the shadow host's parent, beside the custom element (`(body, i)`), so a read through it never lands in the editing host (an earlier version of this entry said it reads as the shadow host itself); one set through the document's `setBaseAndExtent` reads back as given, which is how a unit test that places its caret that way misses the retargeting and a Field falls back to its last known selection (Insert typing and `A` came back wrong, #50). The shadow root's own `getSelection()` reads the same selection unretargeted and with its direction; `getComposedRanges` gives a direction-less `StaticRange`, so it cannot tell a Visual selection's head. Writing needs nothing special: the document's `setBaseAndExtent` and `execCommand` take nodes inside the shadow tree, and the Normal cursor and Visual selection render there. Focus lookup (`composedPath`, `deepActiveElement`) and the lifecycle observer on the Field's root (`Sessions.observeLifecycle`) already covered shadow roots; removing the custom element is a `childList` record on the document.
- **Atoms under editing** (`execCommand('delete')`, `insertHTML`, `ContentEditableField.insertAtom`): a selection from just before to just after a `contenteditable="false"` island or an `<img>` (`(parent, i)` to `(parent, i + 1)`) deletes the whole element. Chromium keeps such a selection as given, and its end may read back as `(nextText, 0)`. Nothing but `insertHTML` brings an element back, and on a non-editable island it misbehaves twice: at the end of a block it puts the element after that block, outside it (`<p>a </p><span contenteditable="false">…</span>`), and it leaves the caret inside the island, where every later command is refused. An `<img>` lands in place. So an undo that writes a U+FFFC back inserts a marker character first, puts the element before it, and deletes the marker; the element's markup is the `outerHTML` the Field kept when its write removed it (the engine's history holds only the U+FFFC). `insertHTML` is thus a third editing command beside `insertText` and `delete`, used only for this restore, and the marker is a U+200B written by `insertText` and deleted by `delete`, so it fires its own `input` events (the Field ignores them while it writes). The marker's two commands are the only steps of a write never offered as a `beforeinput` (`insertMarker`, `deleteMarker`): an editor that takes an offered `insertText` into its model but lets the restore through would keep the U+200B in its model (`tests/unit/atoms.test.ts`, "a page that takes insertText over and lets the restore through is never offered the marker"). The Field also keeps an Atom the page's own editing removed (an Insert-mode Backspace: an Atom it saw at the last read is gone after an `input`), and a restore takes, for each U+FFFC, the latest Atom removed at that U+FFFC's offset (`takeRemovedAtoms`): an undo writes text back where it was, every later change undone first, so the offset names the Atom; newest-first regardless of offset put an earlier `x`'s Atom in the place of a Backspaced one. With none kept at that offset the U+FFFC is written as nothing, the projection may be unchanged, and the Session must not read that as a refusal (`onlyAtomsUnwritten`). Lexical (`onBeforeInput` → `PASTE_COMMAND` → rich-text `onPasteForRichText`) takes no element back through the DOM: after `insertHTML` of a decorator's kept markup its `input` handler read the island's text into the TextNode it had selected and dropped the element, so the whole line became `@cat` (#62). It cancels a `beforeinput` of `insertFromPaste` and does nothing (an `InputEvent` carries no `clipboardData`, which is all it pastes from), so the restore offers that first, the markup as `text/html` (`offerRestore`), and a page that cancels it gets neither the marker nor `insertHTML`; the U+FFFC then stays unwritten, as above. Pinned by `tests/unit/atoms.test.ts`, "a page that takes over the offered restore gets no insertHTML", and `tests/e2e/lexical.spec.ts`, "x on the decorator deletes it; u restores the text around it".
- **Selection and focus** (`Selection.setBaseAndExtent` on a blurred host): setting a selection inside a contenteditable host that does not have focus focuses it, while `setSelectionRange` on a blurred textarea does not. A render while the `:` `/` `?` input has focus would take focus back and close the command line, so `ContentEditableField.setSelection` sets no native selection while the host is blurred; the render on focus sets it. An element marked editable inside an editable root (a Notion block, #69) is never focused itself: `focus()` on it does nothing, the root focused or not, and the root keeps focus while the caret is in the nested one. So such a Field focuses and blurs its outermost editable root and has focus while that root does and the caret is inside it (`ContentEditableField.focusTarget`, `hasFocus`). Pinned by `tests/unit/chromium-facts.test.ts`, "a nested editable is never focused itself" and "an editable root keeps focus while the caret is in a nested editable".
- **beforeinput from the isolated world** (`replaceDomRange` → `run`, `new InputEvent("beforeinput", { targetRanges })`): an `InputEvent` the content script builds and dispatches on the editing host reaches the page's own listeners (`isTrusted` false) with its `inputType` and `data`, and `getTargetRanges()` returns a `StaticRange` over the page's own nodes in the host: DOM objects are shared between worlds, only the JS wrappers differ. A page listener's `preventDefault` reads back in the content script as `defaultPrevented`, which is how a step knows to skip its `execCommand`. A unit test runs in one JavaScript world and cannot show this; pinned by `tests/e2e/refused-edit.spec.ts`, "a page that cancels beforeinput and does nothing refuses the edit".
- **deleteContent is dropped** (`INPUT_TYPE` in `src/field/editingCommands.ts`): Lexical and Slate cancel a synthetic `beforeinput` of `inputType` `deleteContent` and do nothing, so a deletion offered as that would be silently dropped, the `execCommand` skipped. Every deletion is offered as `deleteContentBackward`, which both apply to the target range or the selection. Pinned by `tests/e2e/lexical.spec.ts`, "Lexical cancels a synthetic deleteContent and does nothing", and `tests/e2e/slate.spec.ts`, "Slate cancels a synthetic deleteContent and does nothing".
- **Selection after a settled write** (`Session.finishRender`, Lexical `onSelectionChange`): Lexical takes a script-set selection into its model on a synthetic `selectionchange`, and an offered `insertText` that follows one landed at that selection although the write had reselected its own range and named it in `targetRanges` (observed, cause in Lexical not pinned down). So when a write settles while keys pressed during it wait in a merged render, the Session does not land the mirror's cursor first: that cursor is in text the Field does not hold yet, and Lexical applied the merged write there (`o` typed fast with Esc put `new para` inside the next line, `a headnew parang`). The merged render's write selects its own range. Pinned by `tests/e2e/lexical.spec.ts`, "o and linewise p open a new block below".
- **Slate ignores selectionchange after it renders** (slate-react `Editable`: `state.isUpdatingSelection`, `onDOMSelectionChange`; `WRITE_GAP_MS` in `ContentEditableField`): when a render finds the DOM selection out of step with its model, Slate sets the DOM selection itself and ignores every `selectionchange` until a `setTimeout` it set then has fired, even at a `beforeinput`, which otherwise flushes the selection. Slate takes a deletion at its own selection (it reads `targetRanges` only for insertions and `deleteBy*`), so a write that selects its range in that window deletes at Slate's caret instead: `dd` twice in one burst left `a headin`. The render need not change a node: Slate taking VimText's cursor and putting back its own shows only as a `selectionchange`. So a span is selected only once `WRITE_GAP_MS` (20 ms) have passed since the host's last DOM mutation or the last `selectionchange`, whoever made them. Pinned by `tests/unit/slate.test.ts`, "Slate ignores selectionchange after it renders" (a bare-page probe), and the gap by `tests/e2e/slate.spec.ts`, "u and Ctrl-r restore Slate's text" and "x r cw inside the bold run".
- **Slate takes a selection late** (slate-react `onDOMSelectionChange`, throttled to 100 ms; slate-dom `IS_NODE_MAP_DIRTY`; `replaceDomRange`): Slate takes a `selectionchange` on a throttled timer, so it may take VimText's Normal cursor up to 100 ms after it was set. Its `set_selection` marks the node map dirty until React renders it, a task later; a `beforeinput` in between reads no selection (it neither flushes the DOM selection nor maps `targetRanges` while the map is dirty) and applies the step at the cursor it took, and that render then puts the cursor back into the DOM over the write's range. So a write's first step waits a task after the range is selected, and when the selection is no longer the range then, the write waits out `WRITE_GAP_MS` and selects it again (up to three times). Without the task, `dw` on a bold word deleted only its first letter; without the second selection, `cw` did. Pinned by `tests/e2e/slate.spec.ts`, "dw on a whole bold word deletes it" and "x r cw inside the bold run". A real keystroke's `beforeinput` in that window is applied at the cursor Slate took just the same: `G` then `iZ` typed fast replaced the `l` of `last line` with `Z`, Slate holding `G`'s one-character Normal cursor while the DOM held `i`'s caret (#64). So a character, Backspace or Enter typed in Insert while the caret VimText set is settling (nobody has acted since, and the host changed less than `WRITE_GAP_MS` ago: `ContentEditableField.selectionSettling`) goes into the mirror and lands as a write, as while a write is pending (`Session.typeWhileWriting`). Pinned by `tests/unit/slate.test.ts`, "a character typed right after i, before Slate has rendered the cursor it took late, lands at i's caret".
- **A refused paragraph break, and Slate's late one** (`watchChanges`, `BREAK_WAIT_MS` in `src/field/editingCommands.ts`): Notion cancels a synthetic `insertParagraph` and never makes the break, so the text after it in a write would join the line it was to open; a write stops before that text when the break changed nothing in the host. Slate also cancels it, but makes the break only when React renders, which can come after the step's one task, so a break that has changed nothing by the next step is waited for up to `BREAK_WAIT_MS` (100 ms) before it counts as refused. Pinned by `tests/unit/async-write.test.ts`, "A refused line break no one typed (#73)", `tests/e2e/site-shapes.spec.ts`, "a refused u of J and a refused o", and `tests/e2e/slate.spec.ts`, "o and linewise p open a new block below".
- **Slate puts a stale selection back over a cursor move** (slate-react `Editable`: `readUnsyncedSelection`, `state.pendingSelection`, the layout effect's `setDomSelection`; `holdSelection` in `ContentEditableField`): Slate keeps a `selectionchange` that arrives before its throttled handler runs as a pending selection, which its next render takes instead of resetting the DOM; but it keeps none while its node map is dirty. So when Slate takes VimText's cursor late (the entry above) and VimText moves the cursor again before React has rendered that `set_selection`, the move is dropped and the render puts the cursor Slate took back into the DOM, model and DOM both stale, with nothing to tell VimText it was not the person. Read back, the stale cursor became the mirror's: under load, `G` then `iZ` typed the `Z` nowhere (the Field held a one-character range, and `i` began a text object). The window opens up to 100 ms after any cursor VimText set, so it is met at a person's pace too. So the Field holds the selection VimText last set until the person acts (a key VimText lets through, a pointer, a composition) or a write starts, and when the host's selection moves back to one of the few VimText set before it, the text unchanged, selects the held one again, once, on the `selectionchange` or when the Session next reads the selection, whichever comes first. A move anywhere else is the page's own (a caret it places) and stands, and once only, so an editor that insists has the last word. Pinned by `tests/unit/slate.test.ts`, "G made as Slate takes the cursor before it keeps G's cursor, and a character typed after i lands there".
- **Zero-width no-break space** (slate-react `ZeroWidthString`, `RUN_PATTERNS` in `projection.ts`): Slate holds an empty leaf's place with a U+FEFF (before the placeholder `<br>` of an empty block, beside inline voids). `innerText` reads it, but it renders as nothing and is not in Slate's text, so the projection reads it as nothing, a fourth departure from `innerText` beside the three in "innerText as the oracle" (`innerText` reading it: `tests/unit/chromium-facts.test.ts`, "Zero-width no-break space"). Read as a character, `o` typed fast with text after it wrote the U+FEFF into Slate's model (`new par!a\ufeff`). Pinned by `tests/unit/projection.test.ts`, "a zero-width no-break space is nothing" and "maps around a zero-width no-break space as around nothing", and `tests/e2e/slate.spec.ts`, "o and linewise p open a new block below". A block holding only a U+FEFF and no `<br>` (Quill's cursor blot, which Cmd+B on an empty line leaves, as in Slack's message box) still renders a line, so it projects as an empty line: read as no line, a write's `placeCaret` after `insertParagraph` found no new line, the write stopped before its text, and it was judged refused (#68; `tests/unit/projection.test.ts`, "a block holding only a zero-width no-break space is an empty line"; that it renders a line, `tests/unit/chromium-facts.test.ts`, "a block holding only a U+FEFF and no <br> renders a line").
